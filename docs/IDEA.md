# Agenty — Idea

> **Status**: The proof of concept, the API server, the web frontend and durable runs are done; the next stage is the web portal. This document is the starting point; everything else is built incrementally from it.

## The problem

Enterprises want their teams to build AI agents, but each option on the market falls short:

- Open-source agent builders put governance (SSO, RBAC, audit, policy) behind a paid edition.
- Hyperscaler and SaaS platforms tie the enterprise to one vendor's cloud, models, and pricing.
- Building in-house on agent frameworks makes engineering the bottleneck for every agent.

Agents either stay locked inside IT, or spread without central visibility into what they do, what they access, and what they cost.

## The idea

**Agenty is an open-source, self-hostable platform where teams define their own agents from building blocks the enterprise approves, while every action an agent takes is checked against policy and recorded, without the builder having to think about it.**

The bet is that governance can live in one deterministic place — the path every tool call takes — rather than in the model, the builder's diligence, or a paid edition.

## Core concepts

- **Harness** — a declarative definition (YAML) of an agent: instructions, model, granted tools, limits, and expected output. Model-driven, not a flowchart: the builder describes the situation and the limits; the agent decides the steps. The definition does not depend on any agent framework.
- **Tool** — a typed capability the agent may call, backed by an MCP server.
- **Tool Gateway** — the single path for every side effect. For each call it checks that the tool is granted, evaluates policy, executes, and records the outcome. It also owns the tool servers: it starts the MCP servers that serve a granted tool and stops them when done, so no other code lists or calls their tools. The server keeps a conversation's stopped MCP servers running for its next run, for that conversation alone.
- **Policy** — rules evaluated before every tool call, producing `allow`, `deny`, or `require_approval`. Builders can tighten central policy, never loosen it. Policy only has `deny` and `require_approval` rules, and central and harness policy are evaluated as separate layers, so no layer can change another's rules.
- **Run** — one execution of a harness: the unit of tracing and audit.
- **Conversation** — runs that follow one another: a user's follow-up starts a new run of the harness version the conversation started with, whose model sees the conversation so far before the new input.

## Trust model (the parts that matter from day one)

1. **The model is not trusted.** Safety comes from deterministic controls outside it, not from detecting prompt injection.
2. **Every side effect goes through the gateway.** Nothing else executes tools.
3. **Default deny.** A tool not granted to the harness is denied.
4. **Strictest wins.** Policy results combine as deny > require_approval > allow.
5. **Credentials never reach the model.** They are injected only at call time, never into prompts, logs, or tool output.
6. **Every tool call is recorded** with its policy decision and result.
7. **Runs are private.** A run is seen, continued, cancelled and answered only by the user who started its conversation.
8. **Only auditors read the audit log** of every run, in every workspace; a run's owner sees only their own run's records, in its events. Auditors see what happened, not what was said: tool calls with their arguments, decisions, approvers and results, but no inputs, model replies or transcripts.
9. **The audit log is append-only and tamper-evident.** The database refuses to change or remove a recorded event, and every event is chained to the one before it by a hash. A change made around that, by someone who owns the database, shows as a broken chain, unless everything from the changed event on is written anew. An anchor kept outside Agenty, an event's hash from an earlier export, shows any change up to it; changes after the last anchor kept, removed or added events at the end included, do not show.

## Technology

These choices carry over from earlier exploration and are settled:

- **Go** for the platform: one backend binary, small operational surface. The web frontend is the only part written in another language (see below).
- **Own agent loop** on the official model provider SDKs; no agent framework. Governance has to sit inside the tool-call path, and the harness definition must stay framework-free.
- **OPA (embedded)** as the single policy engine.
- **MCP** as the way tools are reached.
- **`log/slog`** for logging, with `charmbracelet/log` as handler.
- **testify** for Go test assertions.
- **golangci-lint** for static checks, including trust-model rules (e.g. only the Tool Gateway may execute a tool).

For the server and, later, the web portal:

- **gin** for the HTTP JSON API, defined spec-first in OpenAPI: **oapi-codegen** generates the API's Go types and server interface from the spec, and the web frontend generates its client types from the same file.
- **PostgreSQL** as the database, through code generated by **sqlc** on **pgx**, with **goose** migrations embedded in the binary. Until the first release the schema is one initial migration, rewritten rather than migrated: each later rewrite gives it a version number above any it had, the next being 16, so a database from before fails at start instead of running on an older schema, and is reset (`task db:reset`), not upgraded.
- **React with TypeScript and TanStack** for the web frontend: a single-page app talking only to the JSON API, built and deployed separately from the backend, not embedded in it. It lives in `web/`, built with **Vite** and managed with **pnpm**; it uses TanStack **Router**, **Query** and, for the harness form, **Form**. **Tailwind CSS** styles it, with **shadcn/ui** components copied into the repo on accessible Radix primitives, and **react-icons** gives it Lucide's icons. **openapi-typescript** generates its API types from the spec, and **openapi-fetch** calls the API with them.
- **Frontend checks**: **Biome** lints and formats, `tsc` typechecks, **Vitest** with **Testing Library** runs the unit tests against an API mocked with **MSW**, and a **Playwright** smoke test drives the built frontend against a real `agenty serve`.

## Testing

Most code is AI-written, so tests are the primary correctness guarantee:

- **Test-driven**: write the failing test first.
- **Scripted model**: a deterministic `Model` implementation returns predefined responses and tool calls, so the agent loop is tested without a real model. A real-model run is optional and never gating.
- **Invariant tests**: each trust-model guarantee above has a named test that fails if it is violated.
- **High bar for the gateway, policy and secret redaction code**: these are where security lives, and they get the most thorough tests (full coverage, mutation testing when it earns its keep).
- **Table-driven tests**, `require` for preconditions, `assert` for independent checks.

Gates and tooling are added when the code they protect exists, not before.

## Proof of concept

The first goal is to prove the core loop end to end, in a single Go binary:

1. Load a harness from a YAML file.
2. Run an agent loop against one model provider.
3. Call tools on an MCP server, every call passing through the Tool Gateway.
4. Enforce grants and an OPA policy (including `require_approval`, answered on the command line).
5. Write an audit log of every decision and call.

All five are built. `agenty run` ties them together: an operator config (`agenty.yaml`: model provider, MCP servers, central policy) is kept apart from the harness, so builders never touch credentials. Config values come from the environment (`{env: NAME}`, then treated as secrets and redacted everywhere) or are plain text (`{value: TEXT}`). Approvals are asked at the terminal and rejected when stdin is not one. The audit log was a JSON-lines file, one record per decision, approval and result. The gateway starts only the MCP servers whose tools the harness grants, and refuses to start when a granted tool is not served by any of them, so a misconfigured harness fails before it runs.

The API server below has since replaced this standalone command; the operator config, the harness format and the gateway carried over.

**Not in the PoC**: web UI, database, multi-tenancy, identity providers, schedules, knowledge retrieval, sandboxed scripts. Each comes back when the PoC shows it is needed.

## The API server

The PoC held. The next step splits the command line: a server holds the state and runs agents, and the CLI talks to it over HTTP. The trust model carries over unchanged, and so do the gateway, policy and redaction code.

- **Server**: `agenty serve` exposes a JSON API, defined in `schema/openapi.yaml`, and runs agents in its own process. The server's tests check each response they get against that spec. Until it has TLS, it binds to a loopback address only, so tokens never cross a network unencrypted, and it refuses requests for a non-local host, so a DNS-rebound page cannot use it as its own.
- **Sign-in**: a stopgap until OIDC. The operator config lists the users, each with a bearer token of at least 32 characters read from the environment, and redacted like every other secret. Every request must carry a user's token, which the server compares in constant time. A user may use the workspaces they are a member of, and their own runs in them. A user the config marks `auditor: true` also reads the audit log of every workspace, which gives them nothing in a workspace: what they may do there comes from being a member.
- **Workspaces**: harnesses and runs belong to a workspace, and a harness name is unique within one. The operator config lists the workspaces and their members; the API lives under `/v1/workspaces/{ws}`, and a workspace the user is not a member of is not found, as is a run asked for in another workspace than its own. The one exception: a user still reads, never changes, the conversations they started in a workspace they left, or one the config no longer has; reading a run, its conversation, transcript and events is let through for anyone and finds only the user's own runs, and everything else stays not found. `GET /v1/me` names the user and their workspaces, and `GET /v1/workspaces/{ws}` a workspace's members, sorted, to its members: who else is in it is theirs to know, as colleagues on a management page; nothing more about them, such as roles.
- **Browsers**: only pages of the origins the operator config lists under `cors` may call the API; requests from any other page are refused.
- **State**: PostgreSQL holds harnesses, runs, the audit log, which replaces the JSON-lines file and is hash-chained (see the audit log below), and each run's transcript: its conversation with the model, recorded message by message as the run goes, with secrets redacted. Each model reply is also kept in the provider's own form, such as Anthropic's thinking blocks, so a stored conversation can be sent to the model again as it was; that form is for the model alone, and the API's transcripts leave it out. A provider may bind a reply's reasoning to everything sent before it, so each run records digests of its model, instructions and tools and of the earlier conversation it was sent, and each stored message whether redaction changed it from what the model saw. A follow-up sends the provider's form only for the latest runs that had its own model, instructions and tools, were sent exactly what it sends before them, and whose messages it sends as the model saw them; it sends the other replies as their text and tool calls. Each reply also records the tokens of the model call that wrote it, with those read from and written to the prompt cache apart, and each run their sums; a call that fails, such as one whose reply was cut off, is not counted yet. Every changed harness is stored as a new, immutable version, and every run records the version it ran.
- **Harnesses**: managed through the API. The CLI uploads a harness file with its policy files resolved.
- **Approvals**: the server streams each run's events over server-sent events. A call that needs approval suspends its run, which then waits as `waiting`, holding no worker; the request is stored, bound to that call and its arguments, with the results of the calls before it in the same reply. The user who started the run's conversation answers it once, which queues the run, and the audit log records them as the approver; no one else can. A worker resumes the run at the call, which the gateway decides again with central policy as it is then: an answer settles `require_approval`, and only a deny stops the call now. The resumed run keeps its gateway ID; its call counts, denied calls included, come back from its audit log and its steps from its transcript, so a restart neither loosens policy nor resets a limit, and the new decision is recorded under the call's own ID. A call whose arguments hold a secret is denied instead of waiting, as it could only run redacted. The user's waiting requests in a workspace are listed at `GET /v1/workspaces/{ws}/approvals`. One that nobody answers within `approvals.timeout` in the operator config, an hour by default, is rejected, and the run resumes to tell the model so. A waiting run survives a restart, and its event stream replays what it recorded; cancelling it withdraws its request, and its audit log and transcript record that the call did not run. A running run does not survive a server restart.
- **Runs**: each run records the user who started it and the harness version it ran, and belongs to the user who started its conversation: anyone else, other members and auditors too, finds no such run in the workspace. Starting or following up a run queues it, and one of the server's `runs.workers` workers, 16 by default, takes it up, oldest first; a run that cannot start then, as its model cannot be built or its MCP servers do not serve its grants, fails. A queued run outlives a restart, and the next server takes it up. Its owner may cancel a queued, waiting or running run; it then ends as `cancelled`, naming who cancelled it, and interrupting `agenty run` cancels its run.
- **Conversations**: the user who started a conversation may follow up its latest run once it has finished with `POST /v1/workspaces/{ws}/runs/{id}/follow-up`. That starts a new run of the harness version the conversation started with, not the latest, which continues the conversation: a builder's change, a grant taken away included, applies to new conversations only, while central policy, which is not versioned, applies to every call as the server has it at the time. One whose version no longer runs, as an MCP server it needs was removed, cannot be followed up; a new conversation is started instead. The model sees the earlier runs' stored transcripts, redacted again with the secrets configured now, then the new input; offered no tools, it sees earlier tool calls and results as text, as providers refuse tool calls in a conversation without tools. Each run keeps its own transcript, audit log, limits and approvals, so a run stays the unit of audit; the limits bound a run's steps and tool calls, not the conversation's length, which nothing bounds yet, so a long enough conversation fails once it outgrows the model's context window. A run is followed up once at most, and only the conversation's latest run can be, once it has finished, so a conversation never branches. A run that failed or was cancelled, also by a server restart, is continued from where it stopped: the model is told how it ended, and that a call whose result was not recorded may or may not have run; no call is run again, as a tool may not be idempotent. A run that reaches its step limit records the calls it did not make as not run. The operator config's `provider.anthropic.history_cache_ttl`, `5m` by default, can keep the earlier runs in Anthropic's prompt cache for an hour instead, written at twice the input price: each follow-up then writes the conversation so far for an hour, so the next one, even after a pause, reads it from the cache. The first follow-up finds only the first run's own five minutes. The conversation is named by its first run's ID, and `GET /v1/workspaces/{ws}/runs/{id}/conversation` lists its runs, oldest first. `GET /v1/conversations` lists the conversations a user started, whose first run they started, in every workspace, those they left too, the one whose latest run was started last first, each with its workspace, harness, title, its first input cut to 100 characters, and the status of its latest run; `GET /v1/conversations/{id}` finds one the user started, in any workspace. Both only read: a conversation is continued, cancelled and answered through its workspace. A conversation's MCP servers keep running between its runs, so what they hold, such as an open page or a working directory, outlasts a run; they are never shared with another conversation, and stop once idle for `mcp_servers.<name>.idle_timeout`, 15 minutes by default, when the server stops, or with a run cancelled while it ran, as a call may still be running in them; a run that waits for approval holds no call, so it keeps them, also when it is cancelled. Every run keeps its servers, also one never followed up, and nothing bounds yet how many are kept: an operator with heavy servers, such as browsers, sets a short idle timeout. A server the conversation used before that had to start anew, after it stopped or crashed or the server restarted, is named to the model before the new input, as what it held is gone. The CLI starts runs, and never follows one up.
- **CLI**: a client of the API instead of running agents itself. It signs in with the token in `AGENTY_TOKEN`, never a flag, and applies and runs harnesses in the workspace given by `--workspace` or `AGENTY_WORKSPACE`.

To try it (needs [Task](https://taskfile.dev), Docker for the database, Node.js for the example's filesystem MCP server, and `ANTHROPIC_API_KEY` in the environment or a `.env` file at the module root):

```sh
task serve   # starts PostgreSQL with Docker Compose, builds agenty, serves the notes example
task demo    # in a second terminal: applies the notes harness and runs it
```

`task --list` shows the other tasks: `test`, `lint`, `check` (what CI checks), and the database's `db`, `db:stop` and `db:reset`. MCP servers inherit only `PATH`; behind an HTTP proxy, set its variables in the server's `env` in `agenty.yaml`.

The example's central policy asks before every file change and denies dotfiles; its harness allows one rewrite per run. The example's user `demo` works in the workspace `notes`, signing in with `AGENTY_TOKEN`, which the Taskfile sets to a fixed local token unless the environment or `.env` sets another. `agenty run` asks at the terminal. The demo user is an auditor too, so the web frontend's Audit log shows every run's audit records, and the API has them at `GET /v1/audit/runs/{id}`.

## The web frontend

The API server held. This stage put a browser in front of it: the web frontend in `web/`, a client of the JSON API like the CLI, against the API server as it is. The rest of the web portal below comes after.

- **Sign-in**: the user pastes their token, which the frontend checks with `GET /v1/me` and keeps in the browser's `localStorage` until they sign out or the API answers 401. It is sent only in the `Authorization` header, never in a URL, and never logged.
- **Content-Security-Policy**: the built frontend runs only its own scripts, loads stylesheets, fonts and images only from itself (images also as `data:` URLs) and talks only to the API, for good, not until sign-in changes: it shows output from models and tools, which a prompt injection can shape, and the browser holds a token worth stealing, as it may with OIDC too. That output is only ever rendered as text, never as HTML; the policy is the second line of defence. It allows inline styles, which Radix's modal pieces, such as its dialog, lock scrolling with. An injected style cannot send data to another origin, but it could restyle the page, approvals included, misleadingly, or request the frontend's own URLs, so no field holds a secret in its value attribute: the token field is uncontrolled.
- **Theme**: the user's choice of Light, Dark or System is a per-browser preference kept in `localStorage` beside the token, applied as the `data-theme` attribute of `<html>` by a small script of the app's own that runs before the app loads.
- **Layout**: every page of a signed-in user sits beside one sidebar: New chat, the user's recent chats, the management of a workspace, and signing out; on a narrow screen a menu button shows and hides it.
- **Workspaces**: chats are the user's across all their workspaces, and their URLs, `/c/{conversation}`, name no workspace. Managing a workspace happens in that workspace, which is part of those pages' URLs: its overview, at `/w/{ws}`, lists its members, its harnesses and its latest changes, beside its Harnesses and Audit log. The sidebar always names the workspace it manages, with a switcher to another's overview, even when the user has one; pages outside a workspace, such as a chat, manage the user's first.
- **Screens**, in the order they are built: the runs of a workspace, filtered and paged; a run, with its live events, audit log, transcript, and cancel; the waiting approvals, answered before their `expires_at`; the harnesses, with a read-only YAML view and a button that opens a new conversation with it; then the harness form; then the chat app: New chat, an empty chat with a picker of every harness in the user's workspaces whose first message starts its first run, and the sidebar's recent chats. Private runs then removed the runs and approvals pages and the chat's audit log: a user's runs are their chats, and the audit log is the auditors'. Auditors then got the audit log, from a Compliance section of the sidebar: every workspace's runs, filtered by workspace, harness, user and status, each with what the gateway recorded for it, and every event of the log; a workspace's members got its changes, and every user their own activity. Recent chats mark a chat whose run waits for approval, and follow their statuses while a run is under way.
- **Chat**: a conversation's page shows it as a chat, read-only in a workspace the user left: each run's input as the user's message, the model's replies with their tool calls and results folded in, the run's waiting approvals in place, and each run's token usage. A reply box follows up the conversation's latest run once it has finished, saying so when that run failed or was cancelled; the conversation's latest run is followed live. Model text is shown as plain text, not rendered Markdown.
- **Event stream**: browsers' `EventSource` cannot send a token, so the frontend reads a run's event stream with `fetch` and parses it with **eventsource-parser**.
- **Browsers**: the frontend's origin must be listed in the operator config's `cors.origins`; the notes example lists the development server's, `http://127.0.0.1:5173`.

The frontend calls the agenty server at the URL `VITE_AGENTY_API_URL` names when it is built, `http://127.0.0.1:8080` by default. `task web:dev` serves the frontend for development, and `task web:e2e` runs its smoke test, which needs Google Chrome: it signs in, makes a harness, starts a chat with it and follows its runs to their end against a real `agenty serve` with an operator config of its own, `web/e2e/agenty.yaml`, whose dummy model key and closed provider address make every run fail at once, without calling a model; `task check` checks it along with the backend, and `task --list` shows its other `web:` tasks.

## Durable runs

The web frontend held. A run was one goroutine from start to end: a call that needs approval held it, its MCP servers and its events in memory until someone answered or `approvals.timeout` passed, and a restart failed every run in flight. This stage made runs that wait durable, through a job queue in PostgreSQL, built in this order:

- **Pinned conversations**, built: a conversation keeps the harness version it started with, and central policy, not versioned, applies to every call; see Conversations above.
- **A job queue**, built: the runs table is the queue, and there is no queue library; see Runs above. Workers, goroutines inside `agenty serve`, claim queued runs oldest first with `FOR UPDATE SKIP LOCKED`, woken in-process when a run is queued and on start for the runs left queued. A run is never retried, as a tool may not be idempotent. One `agenty serve` serves a database, as yet: on start it fails the runs an earlier one left running.
- **Durable approvals**, built: a run that waits for approval holds no worker and outlives a restart; see Approvals above. MCP servers get no special handling: a resumed call runs on the server there is then, and when that server had to start anew, the call's result says so. That a local server's state may be gone by then is accepted; remote servers over HTTP, the main path once built, keep theirs.

## Next: the web portal

Decided for the stage after durable runs:

- **Frontend**: the web frontend above. Harnesses are authored in a form, with a read-only YAML view.
- **Personal chats**: the portal is a personal chat app first: a user chats with any harness of the workspaces they are a member of, and sees their own conversations. A workspace is where harnesses, and later connectors, are managed. Leaving a workspace makes its conversations read-only: they stay listed and readable, and nothing can be started, followed up, cancelled or answered in them. Membership is read with the config, at a start; a run of someone who left that is still queued or waiting then is cancelled before any worker may take it up, its request withdrawn and its call recorded as not run, and the server does not start if that fails. Running runs end with every start anyway.
- **Audit log**, central compliance evidence, not a workspace tool, built in steps. Built: runs are private to their starter, and organisation-wide auditors, named in the operator config, read every run's audit records, without its input and output, at `GET /v1/audit/runs` and `GET /v1/audit/runs/{id}`. Built: the log is one append-only stream of events, `audit_events`, which the tool gateway's records moved into. Each event names its actor, action, workspace, run or other target, and details, a JSON object in canonical form, and carries the SHA-256 hash of all that and of the event before it, as package `auditlog` computes it. Appends are serialised by a lock, so ids run from 1 without gaps; database triggers refuse every UPDATE, DELETE and TRUNCATE. Auditors export the log as JSON lines with `GET /v1/audit/export` or `agenty audit export`, and `agenty audit verify` checks an export offline and prints its last event's id and hash: the anchor to keep apart from Agenty, which `--anchor` holds a later export to. Limits: the table's owner can disable the triggers; a rewrite that computes every hash anew from some event on verifies on its own, and so does a log whose newest events were removed or forged ones added. An anchor shows any such change up to it, nothing after it: keeping anchors often, outside Agenty, is what makes the log evidence. An export ends with the HTTP trailer `Audit-Export-Complete`, which a proxy that drops trailers would make every export look cut short. Built: the events besides the tool gateway's, a change's event in the change's own transaction, a request before it takes effect: `run.started` (its starter, harness version and the run it follows), `run.cancel_requested` (who asked to stop a queued, waiting or running run; the cancel goes ahead even when the log cannot record the request, as stopping an agent comes first, and the run's end records who cancelled it), `run.finished` on every end (status, steps, error; never input or output), `harness.changed` when a harness gets a new version (who, which version), `server.started` (the central policy modules as written, the users with their roles, the workspaces with their members, the MCP servers with their commands and a digest of their arguments, which may hold a credential; nothing read from the environment). Config is read once, at a start, so the policy and access in force for an event are those of the latest `server.started` before it. Built: the views, one stream seen three ways. Auditors list every event, filtered by actor, workspace, action or run, at `GET /v1/audit/events`; a workspace's members list its changes, its harnesses' new versions, at `GET /v1/workspaces/{ws}/audit`, not its members' runs; and every user lists their own actions, the events they are the actor of, in every workspace, at `GET /v1/me/activity`, which leaves out what others did; what one did in a workspace one left stays, as the chats do. Indexes on actor and on workspace and action keep the two member views fast as the log grows. Auditors' reads are not recorded in the audit log. The web frontend shows them as Compliance → Audit log's Events beside its Runs, Manage → Audit log, and Your activity behind the user's name in the sidebar. Sign-ins come with OIDC: a bearer token has no sign-in moment, and recording failed attempts, before anyone is known, would let anyone fill the log. It is kept forever for now; signing, retention, an external sink, OIDC groups as auditors and service accounts come later. Open: whether auditors see the definition of the harness version a run ran, its grants and policy.
- **Tenancy**: workspaces within one organisation, as the API server has them.
- **Sign-in**: the API server's configured users and tokens are the stopgap: OIDC replaces them before release and is then the only way to sign in.
- **Central policy**: stays Rego files from the operator config; the portal shows it read-only.
- **MCP servers**: reached as local processes over stdio, as today, or as remote servers over HTTP. Their credentials are held by the operator, one set per server.
- **Long conversations**: compress a conversation that nears the model's context window, as Claude Code does, for example with the Anthropic API's server-side compaction, instead of letting it fail.

Conversations started as runs that follow one another, and each run still holds its events in memory while it runs. Longer and more durable conversations keep these in mind:

- **Two tiers of durability**: a chat turn that dies, to a restart or an error, is recovered by continuing the conversation from its transcript, not by resuming the turn where it stopped; a tool call whose result was never recorded is reported to the model as interrupted, never run again, as the tool may not be idempotent. Only runs that wait for approvals are durable, through the job queue and durable approvals; runs that work long on their own come later.
- **Transcript and context**: the stored transcript stays complete and is what users see; what the model sees is derived from it and may be shorter, once conversations are compressed. A conversation becomes an entity of its own, holding that state, its title and its totals, instead of being derived from the runs that follow one another.
- **MCP servers live as long as a conversation**, not a run: a server keeps its state, such as an open page or a working directory, between the turns of one conversation, and stops after it has been idle for a while. A server is never shared between conversations, since its state crosses the boundary, unless the operator marks it stateless. When a server's state is lost, by expiry or a restart, the model is told, as the earlier turns still describe it. Remote servers over HTTP are the main path for a multi-user server; their sessions can outlive a restart, where a local process cannot.
- **A stable prompt prefix**: prompt caching, and on newer Anthropic models the validity of earlier thinking blocks, depend on the instructions, the tool definitions and every earlier message being sent byte for byte as before. Within a conversation they are kept stable, as it keeps its harness version; where they change all the same, earlier thinking is left out rather than sent invalid. Nothing per-request, such as the time, goes into the instructions.
- **Usage**: every model call records its input, output and cache tokens, the basis for conversation budgets, for checking that caching works, and for cost attribution. A conversation gets limits of its own, on tokens or turns, beside each run's.

The longer-term direction stays the same: a governed catalog of tools and skills, service accounts, cost attribution, and a curated starter kit of MCP servers for common enterprise systems — all open source, with no paid edition.
