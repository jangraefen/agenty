# M0 – Scaffolding: design

Status: approved by reviewer · Date: 2026-10-09 · Branch: `chore/m0-scaffolding`

## Goal

An empty but complete skeleton of Agenty, a self-hosted multi-tenant AI agent
builder. Every tool the later milestones rely on is installed, wired up and
exercised by at least one check, so M1–M5 add features, not plumbing.

**Done when:** `task ci` passes locally and in GitHub Actions (including the
Docker image build), the home page renders, the PR has been reviewed by a
reviewer subagent, and the maintainer has approved the merge.

## Non-goals

No auth, tenants, RLS policies, domain tables, LLM calls, workflows or tool
execution. Those belong to M1–M5. M0 only prepares the ground they stand on
(database roles, policy toolchain, test harnesses). Environment variables
needed only by later milestones (`BETTER_AUTH_*`, `ENCRYPTION_MASTER_KEY`)
are added by those milestones.

## Decisions

| Topic | Decision |
|---|---|
| Runtime | Node 24 LTS, pinned in `.nvmrc`, `package.json#engines`, Dockerfile and CI. pnpm pinned via `packageManager`; dependency build scripts are allowed explicitly via `allowBuilds` in `pnpm-workspace.yaml`. |
| Framework | Next.js 16 (App Router), React 19, TypeScript 7 strict plus `noUncheckedIndexedAccess` (Next 16.4 type-checks via the project-local `tsc` CLI by default, which supports TS 7), `output: "standalone"`, long-lived Node server. |
| UI | Tailwind CSS 4, shadcn/ui (`components.json`, `src/components/ui`). TanStack Query is installed with a `QueryClientProvider` in the root layout, though nothing queries yet. English only, no i18n. |
| Lint/format | Biome only, pinned to an exact version: linter, formatter, import sorting, Tailwind class sorting (nursery rule `useSortedClasses` with `functions: ["cn", "cva"]`; its fix is unsafe, applied with `biome check --write --unsafe`), `css.parser.tailwindDirectives`, `vcs.useIgnoreFile`. No ESLint, no Prettier. `task lint` runs `biome ci`. |
| Validation | Zod 4 at every boundary. Environment variables are parsed by a Zod schema in `src/server/env.ts`, lazily (memoised getter), so `next build` never needs runtime configuration. `src/instrumentation.ts` calls it in `register()`, guarded by `NEXT_RUNTIME === "nodejs"` and `NEXT_PHASE !== "phase-production-build"` (dynamic import of the env module), so the server fails fast at startup on invalid configuration. |
| Database | Postgres 18 via `docker-compose.yml`. Drizzle ORM with the `postgres` (postgres.js) driver; migrations generated by drizzle-kit into `src/server/db/migrations` and applied by our own migrate script (see below). |
| Policy | Rego sources in `policies/`, `opa test` for Rego tests, `opa build -t wasm` to `build/policy/policy.wasm` (git-ignored), evaluated in-process with `@open-policy-agent/opa-wasm`. |
| Tests | Vitest with two projects, `unit` (no database or network) and `integration` (real Postgres). Playwright E2E against the production standalone build. |
| Tooling install | `opa` (v1.21.1) is installed by the developer (e.g. `brew install opa`); `task setup` only checks it is on `PATH` and prints install hints otherwise. CI uses `open-policy-agent/setup-opa`; the Docker build stage downloads the pinned binary. |

Exact library versions are taken from npm at implementation time (current
stable), and APIs are checked against the official docs.

## Database roles and schemas

Tenant isolation in M1 depends on RLS, and RLS is silently bypassed by
superusers, table owners and roles with `BYPASSRLS`. M0 therefore separates
the roles from the start:

- `agenty_owner` — owns schema `app` and all its tables; runs migrations
  (`DATABASE_MIGRATION_URL`). Not a superuser, but has `CREATE` on the
  database (the migrator runs `CREATE SCHEMA IF NOT EXISTS`, which Postgres
  checks against the database privilege even when the schema exists; M3's
  workflow world needs it too).
- `agenty_app` — the runtime role (`DATABASE_URL`). `NOSUPERUSER NOBYPASSRLS`,
  owns nothing, cannot create objects in `app`.

**Who creates what:**

- `docker/postgres/init.sql` (run once by the superuser) creates **only the
  two roles** and grants `CREATE ON DATABASE` to `agenty_owner` (built with
  `format(... %I, current_database()) \gexec`, so the database name is never
  hard-coded). docker-compose
  mounts it into `/docker-entrypoint-initdb.d`; CI runs the same script with
  `psql` against its Postgres service container. Postgres runs init scripts
  only on an empty data directory, so changing `init.sql` requires
  `task db:reset` (deletes the volume). Later role changes should therefore be
  migrations wherever possible.
- Migration `0000` (generated by drizzle-kit from `schema.ts`, which exports
  `pgSchema("app")`) creates schema `app`, owned by `agenty_owner`.
- Migration `0001` (`drizzle-kit generate --custom`, hand-written SQL) grants
  `USAGE ON SCHEMA app` to `agenty_app` and sets
  `ALTER DEFAULT PRIVILEGES FOR ROLE agenty_owner IN SCHEMA app GRANT SELECT,
  INSERT, UPDATE, DELETE ON TABLES TO agenty_app` and `USAGE, SELECT ON
  SEQUENCES`. Schema setup is thus versioned and identical everywhere.

drizzle-kit uses `schemaFilter: ["app"]`. Its bookkeeping table stays in the
default `drizzle` schema, owned by `agenty_owner`, with no grants to
`agenty_app`. All tables are referenced schema-qualified via `pgSchema`, so no
`search_path` configuration is needed.

**Applying migrations (amended 2026-10-09, maintainer's choice):** the server
migrates itself on start. `register()` in `src/instrumentation.ts` validates
the environment, takes `DATABASE_MIGRATION_URL` out of `process.env`, and runs
`migrateDatabase()` (`src/server/db/migrate.ts`: drizzle-orm `migrate()` under a
Postgres advisory lock, so several instances starting at once migrate one after
another) before serving; then the owner connection is closed. A failure stops
the server. `task db:migrate` (`node scripts/migrate.ts`, same function) remains
for tests and CI only. Trade-off accepted by the maintainer: the app process
receives owner credentials at start; Node's `process.env` drops them, but the
container configuration and the process's initial environment still hold
them.

**Schemas reserved for M3:** `@workflow/world-postgres` uses three schemas
with hardcoded names — `workflow` (its tables), `workflow_drizzle` (its
migrations) and `graphile_worker` (its job queue). Its bootstrap connects via
`WORKFLOW_POSTGRES_URL`, falling back to `DATABASE_URL`, which would be the
app role. Roles, grants and `WORKFLOW_POSTGRES_URL` are designed in M3; M0
documents the three reserved names in `AGENTS.md`.

**Better Auth tables (M1 note for `AGENTS.md`):** user, session, account,
verification, organization, member and invitation are read before any tenant
context exists and across organizations. They live in `app` but are not
tenant tables; M1 decides their RLS treatment explicitly.

## Application skeleton

```
src/
  instrumentation.ts    # register(): validate env at server start
  app/
    layout.tsx          # html shell, fonts, Providers
    page.tsx            # home page (shadcn Card + Button)
    providers.tsx       # "use client"; QueryClientProvider
    api/health/route.ts # GET → { status: "ok", db: "ok" } or 503
  components/ui/        # shadcn components
  server/
    env.ts              # Zod-parsed process.env (server-only, lazy)
    db/
      client.ts         # drizzle(postgres(DATABASE_URL)), lazy singleton
      schema.ts         # exports pgSchema("app"); no tables yet
      migrations/
    policy/
      evaluate.ts       # load policy.wasm, evaluate(input) → Zod-parsed result
  lib/
    utils.ts            # shadcn cn()
policies/
  agenty/main.rego      # package agenty.authz; default decision = deny
  agenty/main_test.rego
scripts/
  migrate.ts            # `task db:migrate` (tests/CI); the server migrates itself
  check-db.mjs          # fail fast with a hint if DATABASE_URL is unreachable
docker/postgres/init.sql
tests/e2e/              # Playwright specs
```

The empty `auth/`, `agents/`, `tools/`, `workflows/` and `crypto/`
directories from the suggested layout are created by the milestones that fill
them, not as empty placeholders.

`/api/health` runs `select 1` through the app role and returns a body
validated by a Zod schema. It is the only route handler in M0 and
demonstrates the route handler conventions: Zod response schema,
`server-only` imports, no secrets in the error body (a DB failure returns
`{ status: "error", db: "unavailable" }` with HTTP 503 and logs the cause
server-side).

## Policy toolchain

`policies/agenty/main.rego` defines `decision` as a tri-state,
`{ outcome: "allow" | "require_approval" | "deny", reason }`, and denies everything
by default (`outcome: "deny", reason: "no policy matches"`). The entrypoint is
`agenty/authz/decision`. (The project brief named `{ allow, reason,
require_approval }`; the maintainer chose the tri-state on 2026-10-09 because two
booleans allow the meaningless "denied but requires approval".)

`task policy:build` runs
`opa build -t wasm -e agenty/authz/decision --ignore '*_test.rego' -o build/policy/bundle.tar.gz policies`
and extracts only `/policy.wasm` to `build/policy/policy.wasm`. The output
lies outside `policies/`, so later `opa build`/`opa test` runs never pick up
the bundle's `data.json`.

`src/server/policy/evaluate.ts` loads the wasm once from
`path.join(process.cwd(), "build/policy/policy.wasm")` (the standalone
`server.js` changes into its own directory, where the file is traced to),
evaluates an input and parses the output with a Zod schema. It is not wired
to any tool yet. `next.config.ts` sets
`outputFileTracingIncludes: { "/**": ["./build/policy/policy.wasm"] }`, so
the file lands in `.next/standalone` in both the Taskfile and Docker builds;
`task build` fails if it is missing there afterwards.

## Tests

- **Unit (Vitest, `unit` project):** `cn()`, env parsing (valid/invalid),
  policy evaluation of the built wasm (reads the file; no database or
  network).
- **Integration (Vitest, `integration` project):** connects as the app role
  (`DATABASE_URL`) and, for one check, as the owner (`DATABASE_MIGRATION_URL`);
  asserts the guarantees M1's RLS depends on:
  - `select 1` works; the role is neither superuser nor `BYPASSRLS`;
  - `has_schema_privilege(current_user, 'app', 'CREATE')` is false;
  - every table in `app` is owned by `agenty_owner` (vacuous now, guards
    future migrations run as the wrong role);
  - `pg_default_acl` holds the `agenty_owner`/`app` entry granting table
    privileges to `agenty_app`;
  - in a rolled-back owner transaction, a newly created table `app.<tmp>`
    has `has_table_privilege('agenty_app', 'app.<tmp>', 'SELECT')`;
  - the health route handler, called directly, returns `{ status: "ok" }`.
- `server-only` is aliased to an empty module in `vitest.config.ts`, since its
  default export throws outside the `react-server` condition.
- **E2E (Playwright):** `task test:e2e` depends on `build`; Playwright's
  `webServer` starts `node .next/standalone/server.js` on a dedicated port
  (3100) with `HOSTNAME=127.0.0.1` and `reuseExistingServer: false`, so it can
  never silently test a running dev server. Checks that the home page renders
  its heading and that `/api/health` returns `200 { status: "ok" }`.
  Chromium only.

Locally, integration tests run against the dev database. M1's isolation
tests will likely want a separate test database; that is decided in M1.

## Taskfile

All commands run through `Taskfile.yml`, identically locally and in CI.
`dotenv: [".env"]` loads local configuration. `build` and `policy:build` use
`run: once`, so `ci` builds only once.

| Task | Does |
|---|---|
| `setup` | Check Node/pnpm/`opa` are installed (with install hints), `pnpm install --frozen-lockfile`, `pnpm exec playwright install chromium` (CI adds `--with-deps`), copy `.env.example` to `.env` if missing. |
| `dev` | `db:up`, `policy:build`, `next dev` (the server migrates on start). |
| `db:up` / `db:down` / `db:reset` | `docker compose up -d --wait` / `docker compose down` / `docker compose down -v`. |
| `db:generate` | `drizzle-kit generate`. |
| `db:migrate` | `node scripts/migrate.ts` as `agenty_owner` (tests/CI). |
| `db:studio` | `drizzle-kit studio`. |
| `policy:build` / `policy:test` | See *Policy toolchain* / `opa test policies -v`. |
| `lint` | `biome ci .` |
| `typecheck` | `next typegen`, then `tsc --noEmit`. |
| `test` | Depends on `policy:build`; `vitest run` (both projects). |
| `test:e2e` | Depends on `build`; `playwright test`. |
| `build` | `policy:build`, `next build`, copy `public/` and `.next/static` into the standalone output, verify the wasm is present there. |
| `docker:build` | `docker build .` (run as a separate CI job). |
| `ci` | `policy:test → lint → typecheck → check-db → db:migrate → test → build → test:e2e`. `check-db` (`scripts/check-db.mjs`, Node only, no `psql` needed) fails early with "run `task db:up`" when `DATABASE_URL` is unreachable. |

## Infrastructure

- **`docker-compose.yml`:** `postgres:18`, port configurable via
  `POSTGRES_PORT` (default 5432), named volume mounted at
  `/var/lib/postgresql` (the Postgres 18 image's layout), healthcheck, init
  script.
- **`Dockerfile`:** multi-stage on `node:24-*-slim`: deps (pnpm via
  corepack) → build (downloads the same pinned `opa` for `policy:build`; no
  runtime env needed thanks to lazy env parsing) → runtime with the
  standalone output and the migrations folder, non-root user,
  `HOSTNAME=0.0.0.0`, `PORT=3000`.
- **`.env.example`:** `POSTGRES_USER`/`POSTGRES_PASSWORD` (superuser for
  compose and the init script), `POSTGRES_PORT`, `DATABASE_URL`,
  `DATABASE_MIGRATION_URL`. Values are local-development defaults, not
  secrets.
- **GitHub Actions (`.github/workflows/ci.yml`):** on push and pull request.
  Job `ci`: checkout, Node 24, pnpm, go-task, `open-policy-agent/setup-opa`
  (v1.21.1), pnpm store cache; Postgres 18 service container; run
  `docker/postgres/init.sql` with `psql`; `task setup` (Playwright with
  `--with-deps`); `task ci`; upload the Playwright report on failure. Job
  `docker`: Postgres 18 service plus `init.sql`, `task docker:build`, then
  start the image against the empty database (`docker run --network host`) and
  poll `/api/health`, which proves the image migrates itself on start.

## AGENTS.md

(Amended 2026-10-09: the agent instructions live in `AGENTS.md`, which `next dev` also
maintains a managed block in; `CLAUDE.md` only imports it with `@AGENTS.md`.)


Describes the architecture (layers, folder layout, the two DB roles, who
creates schemas and grants, the three schemas reserved for the workflow
world, the Better Auth table note), the non-negotiable rules from the brief
(tenant only from the session, RLS per transaction, `withPolicy` around every
tool, idempotency keys, encrypted secrets that never reach prompts/logs/
responses, tool descriptions and results are untrusted), conventions (Biome,
Zod at boundaries, `server-only`, lazy env, tests per guarantee, English) and
the key `task` commands. It is updated by every milestone.

## Risks

- **Vitest 5 / Next 16 / Tailwind 4 / Biome 2 compatibility:** verified while
  scaffolding; incompatibilities are resolved by following the official docs
  rather than pinning old versions, and noted in `AGENTS.md` if a workaround
  is needed.
- **`@open-policy-agent/opa-wasm`** was last published in 2024; it is the
  mandated library and the WASM ABI is stable, and M0's unit test is what
  proves it works with the current `opa` release.
- **pnpm build-script approvals:** new dependencies with install scripts need
  an `allowBuilds` decision; CI's frozen install surfaces missing ones.
