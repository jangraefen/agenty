# M1 – Auth and workspaces: design

Status: approved by reviewer · Date: 2026-10-09 · Branch: `feat/m1-auth-workspaces`

## Goal

Users can sign up and sign in with email and password, belong to one or more
**workspaces** (the tenant), switch between them and manage members. All later
domain data is isolated per workspace by Postgres row-level security (RLS),
and that isolation is proven by tests.

**Done when:** `task ci` passes locally and in GitHub Actions, the isolation,
auth and E2E tests below exist and pass, the PR has been reviewed by a reviewer
subagent and the maintainer has approved the merge.

## Terminology

- **Workspace** = tenant. It is the unit of data isolation: every domain table
  has `tenant_id` referencing a workspace, and RLS keys on it. The database
  keeps the names `tenant_id` and `app.tenant_id` (brief); everything a user
  sees and our own code APIs say "workspace".
- **Organization** is reserved for a later milestone (OIDC/SAML single sign-on):
  an organization will own several workspaces and the SSO connections. M1
  builds nothing for it, but avoids the name so it stays free. Better Auth's
  "organization" plugin is used as the engine for workspaces (see below); its
  name appears only inside `src/server/auth/` and the client wrapper.

## Non-goals

- Email of any kind (no SMTP; runtime is app + Postgres only): no email
  verification, no invitation emails, no password reset. A member who loses
  their password is removed and re-invited by an owner/admin. SMTP can be added
  later behind an interface.
- Organizations, SSO, teams, custom roles / dynamic access control.
- Deleting workspaces, deleting user accounts, changing email.
- Domain tables (agents etc. arrive in M2). M1 delivers the RLS machinery and
  proves it on a test fixture table.

## Decisions

| Topic | Decision |
|---|---|
| Library | Better Auth (current stable, 1.7.x) with the Drizzle adapter (`better-auth/adapters/drizzle`, `provider: "pg"`, `transaction: true`) and the organization plugin, plus `nextCookies()` (last plugin). |
| Auth tables | New schema `auth`, owned by `agenty_owner`; `agenty_app` gets `USAGE` plus table/sequence privileges via default privileges (same pattern as `app`). **No RLS** on `auth` tables: Better Auth reads them before a tenant is known and across workspaces, and it runs its own queries and transactions, so `app.tenant_id` cannot be set for them. Instead, only `src/server/auth/**` may import the auth schema/instance (enforced by a Biome `noRestrictedImports` rule), and it scopes every workspace-related read by the session's user. **Accepted risk:** these tables hold password hashes and session tokens and are readable by `agenty_app`; raw SQL through `getDb()` elsewhere could reach them. Mitigations: the import rule, no raw SQL against `auth` outside `src/server/auth/` (reviewed), Drizzle's parameterised queries. A separate auth role remains possible later. |
| Table names | Renamed through the plugin's `schema` option: `workspace`, `workspace_member`, `workspace_invitation`, foreign key columns `workspace_id`. Core tables: `user`, `session`, `account`, `verification`, plus `rate_limit`. Columns are snake_case. The session's active-workspace column is renamed to `active_workspace_id` only if the plugin supports renaming that field (unverified); otherwise it stays `active_organization_id` and only `src/server/auth/` knows it. The first plan task verifies every rename and records which internal names stay. |
| Schema source | `src/server/db/auth-schema.ts` is **hand-maintained**: written once from the Better Auth CLI output (`auth generate`, which emits plain `pgTable` without a pg schema), then moved to `pgSchema("auth")` with our names. `task auth:generate` writes the CLI output to `build/auth-schema.generated.ts` (git-ignored) for diffing after Better Auth upgrades; it never overwrites the committed file. Migrations are generated by drizzle-kit as usual. The adapter maps by model key, so the `auth` tables are passed in its `schema` option. |
| IDs | `advanced.database.generateId: "uuid"`; id and foreign key columns are `uuid` (the CLI's uuid output already uses `uuid` columns). `tenant_id` must be `uuid`. |
| Passwords | Email/password only, Better Auth default hashing (scrypt), `minPasswordLength: 12`, `maxPasswordLength: 128`, no email verification. |
| Sessions | Database sessions, cookie cache **off** (Better Auth's default, pinned explicitly), so membership/role changes and sign-out take effect immediately. Secure cookies in production. |
| Rate limiting | Better Auth rate limiter, `storage: "database"` (correct with several instances), Better Auth's default rules. The limiter keys on the client IP; without a trusted IP header Better Auth falls back to one shared bucket per path, which would let one client lock everyone out of sign-in. Therefore `AUTH_IP_HEADER` (e.g. `x-forwarded-for`) configures `advanced.ipAddress.ipAddressHeaders`; README says to set it **only behind a reverse proxy that overwrites the header**, since otherwise clients can spoof their IP. The server logs a warning at start when `AUTH_RATE_LIMIT=false` in production. `AUTH_RATE_LIMIT` (`"true"`/`"false"`, default `true`) exists so Playwright and the Docker smoke test, which sign in repeatedly from one IP, can switch it off explicitly; an integration test proves the limiter rejects repeated sign-in attempts when on. |
| Sign-up | Open, unless `AUTH_DISABLE_SIGNUP=true`. Even when disabled, sign-up is allowed (a) if no user exists yet (bootstrap of a fresh install) and (b) for an email with a pending, unexpired invitation. Enforced server-side in `databaseHooks.user.create.before`, which every user-creation path goes through; it reads through the hook's transaction-bound adapter and rejects with `APIError("FORBIDDEN", { code: "SIGNUP_DISABLED" })`, which the UI maps to "Sign-up is disabled on this instance". The UI only mirrors the rule. Two concurrent bootstrap sign-ups may both succeed; accepted. Only email/password sign-up exists; a test pins the configured plugin list, so adding a plugin that creates users (social, magic link, admin) forces re-checking the gate. |
| Personal workspace | Every user has at least one workspace. Better Auth runs `user.create.after` hooks only after the sign-up transaction commits, and `session.create.before` runs inside it, so the workspace is created in **`databaseHooks.session.create.before`**: if the user has no membership, it creates "<name>'s workspace" and an `owner` membership, then sets the session's active workspace to it. The rows are written through the **transaction adapter** from Better Auth's AsyncLocalStorage (`getCurrentAdapter(ctx.context.adapter)` / `runWithTransaction`; `ctx.context.adapter` alone is the base adapter on another connection and would fail the foreign key to the uncommitted user), with the plugin's internal model and field names (`organization`, `member`, `organizationId`), which the adapter maps to our renamed tables. The work runs inside a transaction (the sign-up one, or its own on paths without one) after `pg_advisory_xact_lock(hashtext(userId))` and re-checks for a membership, so concurrent sign-ins cannot create two workspaces and a failure leaves no orphan workspace. On sign-up a failure rolls back the whole sign-up. If no endpoint context is available, the hook throws (fail closed: no session without a workspace). Writing the rows directly bypasses the plugin's create endpoint and its organization hooks; this is intended (we use none). The first plan task proves, with integration tests, hook order, transaction scope, the import path of `getCurrentAdapter`, and the model mapping for the renamed tables, before anything builds on it. |
| More workspaces | Every user may create further workspaces (creator becomes `owner`); no limit in M1. |
| Slugs | The plugin requires a unique slug. We generate `ws-` + 10 random lowercase alphanumerics for every workspace; slugs are never shown or used in URLs (the active workspace lives in the session). |
| Roles | Plugin defaults: `owner`, `admin`, `member`. Owner/admin: rename workspace, invite, cancel invitations, change roles, remove members (plugin rules: only an owner can make/demote/remove owners; the last owner cannot leave or be demoted). Member: view members, leave. |
| Invitations | No email: `sendInvitationEmail` is not configured (or a no-op if required). Creating an invitation returns its id; the UI shows a copyable link `/invite/<id>`. Accepting requires being signed in with the invited email address (the invite page offers sign-in and sign-up, sign-up pre-filled with the invited email). Expiry: plugin default (48 h). **The invitation id is a bearer secret bound to an email nobody has verified** (no email in M1): whoever holds the link can sign up with that email and accept. Therefore only owners/admins ever see invitation ids: the settings page shows invitations only to them; a Better Auth `hooks.before` rejects list-invitations for members; and get-full-organization (which includes invitations and backs the client's `useActiveOrganization`) is not on the endpoint allowlist; the UI uses get-organization + list-members instead. The user-side list of one's own invitations already requires a verified email and stays closed. README and the UI ("share this link only with the invitee") say so. |
| Active workspace | The session's active-workspace column. Set on session creation (`databaseHooks.session.create.before`, see Personal workspace) to the user's oldest membership; changed by the switcher (`setActiveOrganization`). If the active workspace is no longer valid (member removed), the shell switches to the oldest remaining membership; with none left, it shows a "create a workspace" screen for the rest of that session, and the next sign-in creates a fresh personal workspace (see above). Being removed from every workspace therefore never locks a user out of the instance; they keep their account with an empty workspace. |
| Plugin endpoints | Our own code takes the workspace only from the session. The plugin's endpoints take an organization id from the body/query and check membership and role themselves; **Allowlist** enforced in `hooks.before`: every `/organization/*` endpoint not listed is rejected with 404. Allowed: create, update (name), set-active, list (own), get-organization, invite-member, cancel-invitation, list-invitations (owner/admin only), get-invitation, accept-invitation, reject-invitation, list-members, update-member-role, remove-member, leave. Everything else (teams, dynamic roles, delete, get-full-organization, …) is rejected; a test asserts that an unlisted endpoint returns 404. |
| Configuration | New env vars, Zod-validated in `getEnv()`: `BETTER_AUTH_SECRET` (≥ 32 chars), `BETTER_AUTH_URL` (http(s) URL; also the only trusted origin, so Playwright, port 3100, and the Docker job, port 3000, each pass their own), `AUTH_DISABLE_SIGNUP` and `AUTH_RATE_LIMIT` (`"true"`/`"false"`), `AUTH_IP_HEADER` (optional header name). `.env.example` gets development values; the Docker CI job and Playwright pass them explicitly. The Better Auth instance is created lazily (`getAuth()`), so `next build` still needs no runtime env. |

## Tenant context

`src/server/auth/tenant.ts` (server-only):

```ts
declare const brand: unique symbol;
export type TenantContext = {
  readonly userId: string;
  readonly workspaceId: string;
  readonly role: "owner" | "admin" | "member";
  readonly [brand]: true;
};
export async function getTenantContext(): Promise<TenantContext>;
```

- Loads the session from the request headers; no session → `UnauthorizedError`.
- Takes `active_workspace_id`; none → `NoWorkspaceError`.
- **Re-reads the membership** (`workspace_member` for user + workspace) on
  every call; no membership → `ForbiddenError`. So a removed member loses access
  on their next request even though their session still names the workspace.
- Our code never takes the workspace id from a request body, query string or
  header. `TenantContext` can only be constructed in this module (branded
  type).

`src/server/db/tenant.ts` (server-only):

```ts
export async function withTenant<T>(ctx: TenantContext, fn: (tx: Tx) => Promise<T>): Promise<T>;
```

Opens a transaction on the `agenty_app` pool, runs
`select set_config('app.tenant_id', ${ctx.workspaceId}, true)` and then `fn(tx)`.
Domain code reads and writes domain tables only through `withTenant`.

## RLS for domain tables (`app` schema)

`src/server/db/tenant-table.ts` provides the building blocks M2+ use for every
domain table:

- `tenantId()` column: `tenant_id uuid not null references auth.workspace(id) on delete cascade`.
- `tenantIsolation(table)` policy (Drizzle `pgPolicy`, `as: "permissive"`, `for: "all"`,
  `to: agenty_app` declared with `pgRole(...).existing()`):
  `USING` and `WITH CHECK` both
  `tenant_id = nullif(current_setting('app.tenant_id', true), '')::uuid`.
  Without a tenant set, the expression is `NULL`: nothing is visible and every
  write fails.
- RLS enabled on the table (Drizzle `enableRLS`/policy generation).
- No `FORCE ROW LEVEL SECURITY`: only the owner bypasses RLS, the owner
  credentials are removed at server start, migrations legitimately need
  cross-tenant access, and an existing test asserts that `agenty_app` neither
  owns tables nor is a member of any role.

**Catalog guard** (integration test): every table in schema `app` has a
`tenant_id uuid not null` column, `relrowsecurity = true`, and a policy for
`agenty_app` whose `USING` and `WITH CHECK` reference `app.tenant_id`. With no
tables in M1 it passes vacuously, and a test proves the guard fails on a
fixture table without RLS. Exceptions (should a global table ever be needed)
must be listed explicitly in the test with a reason.

## Isolation tests

Integration tests run as `agenty_app` against a fixture table built with the
same helpers, in a test-only schema `rls_fixture` that the test setup creates
(as `agenty_owner`) and drops. They prove:

1. In workspace A's context only A's rows are visible (select, count, join).
2. With no tenant set, nothing is visible and inserts fail.
3. As A, inserting a row with B's `tenant_id` fails (`WITH CHECK`).
4. As A, updating a row's `tenant_id` to B fails; updating/deleting B's rows
   affects zero rows.
5. `set_config(..., true)` does not leak: on a `max: 1` pool, after A's
   transaction commits **or rolls back**, the next transaction on the same
   connection sees nothing.
6. A malformed `app.tenant_id` raises an error instead of returning rows.
7. `withTenant` passes the workspace id as a bind parameter (a value
   containing SQL is treated as data and fails the uuid cast).
8. `getTenantContext` rejects a workspace the user is not (or no longer) a
   member of, and a session without active workspace.

## Auth behaviour tests

Integration (via `auth.api` against the real database):

- Sign-up creates the user, a personal workspace with the user as `owner`, and
  a session whose active workspace is that workspace; if creating the
  workspace fails, no user is left behind.
- Sign-up gate: with `AUTH_DISABLE_SIGNUP=true`, sign-up is rejected when users
  exist and no invitation is pending; allowed with a pending invitation for that
  email; allowed for the first user (bootstrap, on an empty `user` table — run in
  a way that does not depend on other tests' data, e.g. the gate's decision
  function tested as a unit with the DB lookups injected, plus one integration
  test of the invited path).
- Accepting an invitation while signed in with a different email fails; with
  the invited email it adds the member with the invited role.
- A `member` cannot create invitations or change roles, and gets no invitation
  ids from any endpoint (list-invitations rejected, get-full-organization not
  allowed).
- An `/organization/*` endpoint outside the allowlist returns 404.
- Two concurrent sign-ins of a user without membership create exactly one
  personal workspace.
- The configured plugin list is exactly the expected one.
- With `AUTH_RATE_LIMIT` on, repeated failed sign-ins are rejected with 429.
- Error responses contain no internal details.

E2E (Playwright, production build):

- Sign up → lands in the app shell with "<name>'s workspace" active.
- Create a second workspace, switch between them; the switcher shows the
  active one.
- Owner invites a new email as `member`, copies the link; in a second browser
  context the invitee signs up via the link and sees the workspace; the member
  sees no invite controls.
- Signed-out access to an app page redirects to `/sign-in`.

## UI and routes

- `src/app/api/auth/[...all]/route.ts`: `toNextJsHandler(getAuth())`.
- `/sign-in`, `/sign-up` (hidden link when sign-up is disabled), `/invite/[id]`.
- Signed-in shell (route group) with a header: workspace switcher (list,
  switch, "New workspace" dialog) and user menu (name, email, sign out).
- `/`: signed out → the landing page (M0 heading stays) with sign-in/sign-up
  buttons; signed in → workspace home placeholder ("Agents arrive in M2").
- `/settings/workspace`: rename (owner/admin), members table (role change,
  remove; owner/admin), pending invitations and invite form (email + role;
  both owner/admin only), "Leave workspace" for non-last-owners.
- `src/proxy.ts`: optimistic redirect to `/sign-in` for app routes when no
  session cookie is present (`getSessionCookie`); pages and route handlers
  always validate the session themselves.
- Forms use shadcn/ui components; client calls go through `src/lib/auth-client.ts`
  (`createAuthClient` + `organizationClient()`), wrapped by small hooks named
  in workspace terms. Validation messages from Zod; errors shown inline,
  never raw server errors.

## Database and migrations

- Migration: `CREATE SCHEMA auth`, `GRANT USAGE ON SCHEMA auth TO agenty_app`,
  default privileges for `agenty_owner` in `auth` (tables: select, insert,
  update, delete; sequences: usage, select), then the generated tables.
- `roles.int.test.ts` is widened to schema `auth` (owned by `agenty_owner`,
  all tables owned by `agenty_owner`, app role cannot create objects there) and
  pins schema `USAGE` and sequence privileges for both schemas.
- Integration tests keep using the dev database; they create users with unique
  emails (`<test>-<random>@test.invalid`) and delete their users and
  workspaces afterwards (memberships, invitations, sessions and `app` rows
  cascade). Auth tests live next to the code as `src/server/auth/*.int.test.ts`.
  A separate test database is not needed in M1.

## Risks

- **TypeScript 7 and Better Auth's inferred types** (`$Infer`, plugin types):
  checked in the first plan task; if inference breaks, we type the few
  session/workspace shapes we need explicitly with Zod.
- **Generated schema vs. custom names/uuid**: verified in the first plan task
  by generating and inspecting the output before anything builds on it.
- **Cache Components**: pages that read the session are dynamic; they read
  headers inside `Suspense` boundaries or call `connection()`, following the
  Next 16 docs in `node_modules/next/dist/docs/`.
